# Go TUI MVP plan

Date: 2026-09-20. Status: P0 and P1 merged; M0 in review.

## Goal

A Go terminal client for `voss serve`, built on Bubble Tea v2, that a person can use for a normal day of work. It replaces the Rust `crates/voss-tui` and becomes the candidate to replace the in-process Textual TUI once it catches up.

The MVP is done when:

1. It does everything `crates/voss-tui` does today: spawn or attach, `doctor`, `sessions`, `resume <id>`, streaming chat, mode switching, abort, permission prompts, cost and token display.
2. It adds the client-side features from pi that need no server changes (M3 below).
3. `VOSS_USE_TUI=1 VOSS_TUI_BIN=<go binary> voss` launches it through the existing dispatcher in `voss/cli.py`, with no Python changes.
4. The cold pass in "Testing" passes.

## Decisions

| Topic | Decision | Why |
|---|---|---|
| Location | `tui/` at the Voss repo root, its own module `github.com/vosslang/voss/tui`, with `replace github.com/vosslang/voss/sdk/go => ../sdk/go` | Sits next to `contracts/openapi.json` and the SDK drift tests. Keeps Bubble Tea out of the SDK module's dependencies. |
| Binary name | `voss-tui-go` during the MVP, renamed to `voss-tui` when the Rust client is retired | The dispatcher and cargo-dist already use `voss-tui` for the Rust binary. |
| Libraries | `charm.land/bubbletea/v2` (v2.0.9), `charm.land/bubbles/v2` (v2.2.1), `charm.land/lipgloss/v2` (v2.0.6), glamour for markdown | Bubble Tea v2 probes for synchronized output (mode 2026), supports the Kitty keyboard protocol and bracketed paste, and `tea.Println` writes lines above the program. |
| Screen mode | Inline, keeping normal scrollback, not the alt screen | Same as pi and omp. Finished blocks go to scrollback once with `tea.Println`; only the live region is redrawn. |
| Rust client | Frozen now, deleted when the Go MVP is done | Three TUIs is two too many. |

## Architecture

```
tui/
  main.go          flags: --attach URL --token T, --cwd, --model; subcommands doctor, sessions, resume <id>
  app/model.go     root Bubble Tea model: session state, focus, overlays
  app/events.go    pure reducer: (state, voss.TypedEvent) -> (state, []block to commit)
  app/stream.go    one SSE subscription per session, fed into the program as tea.Msg
  ui/editor.go     multiline editor on bubbles/textarea plus the key map
  ui/transcript.go block renderers: user, assistant (markdown), tool row, plan, clarify, warning
  ui/footer.go     model, mode, tokens, cost, context %, working indicator
  ui/permission.go the permission prompt
  ui/complete.go   slash, @file and path completion popups
```

Rules that follow from how the server behaves today:

- **Open one SSE stream per session and keep it open for the session's life.** The server cancels the running turn when the stream drops (`app.py:779`), and a second subscriber on the same session takes events away from the first. The Rust client opens a stream per turn and stops at `session.idle`. Don't copy that.
- **Keep a message queue in the client.** The server returns 409 while a turn runs. Pressing Enter mid-turn queues the message; the queue sends on `session.idle`.
- **Draw the working indicator in the client.** The server sends no working events. Show a spinner, elapsed time and the Esc hint from message send until `session.idle`.
- **Keep the event reducer a pure function.** Event handling is where the bugs will be, and a pure reducer can be tested with recorded SSE captures and no terminal.
- **Handle `UnknownEvent`.** Show a one-line dim notice so a newer server is visible instead of silent.

Permission prompt: the server sends `permission.updated{id, tool_name, args, dimension}`. For `tool_name == "scope_expand"` offer y/n. Otherwise offer allow once (`a`), always (`A`) and deny (`d`). Reply with `PermissionReply`. A `stale` reply means another path already answered it, so dismiss the prompt without an error.

## Key map

pi and Claude Code conventions, not the Rust client's:

| Key | Action |
|---|---|
| Enter | send, or queue if a turn is running |
| Shift+Enter, Ctrl+J | newline |
| Shift+Tab | cycle mode plan, edit, auto (the Rust client used Tab, which completion needs) |
| Tab | complete path or slash command |
| Esc | abort the running turn, else close a popup, else restore the last queued message into the editor |
| Ctrl+C | clear the editor; twice within 1s quits |
| Ctrl+D | quit when the editor is empty |
| Ctrl+R | search prompt history |
| Ctrl+G | edit the prompt in `$EDITOR` |
| Ctrl+O | expand or collapse the last tool row's arguments |

## Milestones

Each task lists how to check it. Line counts are estimates.

### M0. Skeleton and non-interactive commands (about 400 lines)

| Task | Check |
|---|---|
| Module, `main.go`, flags; spawn through `voss.Spawn` with `Cwd`, or attach with `--attach/--token` | `voss-tui-go --attach ... doctor` and a spawned `voss-tui-go doctor` both print the report |
| `sessions` lists saved sessions for the cwd | output matches `voss sessions` for the same repo |
| Clean shutdown: `Client.Close` on every exit path, including a panic in the program | no `voss serve` process left after quitting, checked with `pgrep -f "voss serve"` |

### M1. Chat loop, parity with the Rust client (about 1,200 lines)

| Task | Check |
|---|---|
| Session create, long-lived SSE stream, reducer for `server.connected`, `user`, `thinking`, `stream.delta`, `stream.finalize`, `final`, `status`, `session.idle` | reducer tests pass on the SSE captures in Voss-ADE `docs/reference/harness/` and on a fake-turn run |
| Editor, send, streaming text in the live region, block committed to scrollback on finalize | a 3-turn conversation scrolls back correctly in iTerm2, Ghostty and tmux |
| Footer from `status` events: model, mode, tokens, cost, context % | values match `GET /session/:id/cost` after a turn |
| Working indicator, Esc abort | abort mid-stream returns to idle; the next message works |
| Permission prompt with a/A/d and y/n | in edit mode, an `fs_edit` prompts; `A` stops later prompts for that file; `d` shows the denial |
| Mode cycle; the mode is sent with each message | a plan-mode turn makes no edits |
| 409 and error handling: queue on busy, `VossError` detail shown in the transcript | two quick Enters send in order; stop the server mid-session and see a readable error, not a crash |

### M2. Transcript rendering (about 1,000 lines)

| Task | Check |
|---|---|
| Markdown with glamour. While streaming, re-render the in-progress block on each delta, capped at 30 fps; commit on finalize | no visible jump at the end of a response |
| Tool rows: name, one-line summary, state; Ctrl+O shows arguments | a turn with 5 tool calls shows 5 rows, not 10 |
| Plan, clarify, warning, overflow and `UnknownEvent` blocks | each has a reducer test with a fixture |
| Word-level diff rendering of `fs_edit` arguments in the permission prompt | an edit prompt shows old and new text with changes highlighted |
| Width handling: wrap to terminal width, re-render the live region on resize; committed scrollback is not re-flowed | resize from 120 to 60 columns mid-stream without garbled lines |

### M3. Client-side features from pi (about 1,500 lines)

| Task | Check |
|---|---|
| Emacs keys in the editor: Ctrl+A/E/K/U/W, Alt+D, kill ring (Ctrl+Y, Alt+Y) | unit tests on the editor model |
| `@` fuzzy file mention over the cwd, respecting `.gitignore` | `@appgo` finds `server/app.go` in a test tree |
| Tab path completion | completes a nested path in two presses |
| Paste over 10 lines collapses to `[paste #1 +N lines]` and expands on send | paste a 200-line file; the editor stays readable and the full text is sent |
| Prompt history saved to `~/.config/voss/tui-history`, next to the harness config, Ctrl+R search | history survives a restart |
| Ctrl+G opens `$EDITOR` | edited text comes back into the editor |
| Message queue shown above the editor; Esc restores the last queued item | queue 3 messages mid-turn; they send in order |
| Slash palette over client-side commands: /help /cost /clear /mode /sessions /resume /doctor /copy /quit | each works; unknown commands say "not available in this client" and are not sent as prompts |

### M4. Resume, dispatcher and cut-over (about 300 lines)

| Task | Check |
|---|---|
| `resume <id>` and `/resume` picker via `SessionOptions.Resume` | a resumed session answers a question about the earlier turns |
| Dispatcher: `VOSS_USE_TUI=1 VOSS_TUI_BIN=$(which voss-tui-go) voss` | bare `voss` opens the Go client |
| Delete `crates/voss-tui`, rename the binary to `voss-tui`, switch the cargo-dist entry to a Go release step | release dry run produces the Go binary for the four targets |

The Textual TUI stays the default after M4. Switching the default is a separate decision that needs the server work below.

## Out of scope for the MVP (needs server work first)

Each needs a new endpoint or event. Do them as pairs, one server change plus the client feature it unlocks, after the MVP:

| Client feature | Server change |
|---|---|
| Tool rows that update in place with output and timing | `call_id`, output and duration on `ToolEvent` (dropped in `server/renderer.py:108`) |
| Model picker and switching models mid-session | a model list endpoint and a model field on the message or session |
| Server slash commands (/budget, /why, /diff, /undo, /memory...) | a slash list and dispatch endpoint |
| Transcript on resume | a session history endpoint (the Rust client reads `.voss/sessions/*.json` from disk) |
| Reconnect without losing events | `id:` on SSE frames and `Last-Event-ID` replay |
| Per-hunk diff review | a diff-proposal event and a reply route |
| Agent tree, fork, `/tree` | subagent events; the server currently ignores `parentID` |
| Images in prompts | non-text message parts |
| Real steering mid-turn | a steer endpoint wired to `run_turn`'s `steer_inbox` |

## Testing

- **Reducer tests:** table tests from recorded SSE, one fixture per event type, plus a whole-turn capture.
- **Render tests:** golden files for each block at 60 and 120 columns.
- **Integration:** run against `VOSS_SERVE_FAKE_TURN=1` through `.venv/bin/voss`, the same as the SDK tests; skip when no executable resolves.
- **Cold pass before calling the MVP done:**
  - fresh terminal, new project with no `.voss/`
  - 60-column window, resize during a stream
  - tmux, and inside a Voss-ADE terminal pane (xterm.js)
  - quit during a stream, then `resume`
  - a permission prompt in every mode
  - check `pgrep` for leftover servers

## Risks

- **P1 slips.** Then the Go client should refuse to start in a project that has `.voss/safety.yml` or `.voss/permissions.yml`, rather than run without them.
- **Inline rendering in xterm.js.** Voss-ADE renders terminals with xterm.js, which does not support every sequence. Test M1 inside an ADE pane early.
- **ADE agent detection.** Voss-ADE detects a Voss pane from the `python -m voss.cli` or `bin/voss` process. A Go process won't match. It needs a detector entry in Voss-ADE (follow-up there).
- **Scope creep toward omp.** omp's interactive mode is about 75k lines. The MVP stops at pi-level client features.
