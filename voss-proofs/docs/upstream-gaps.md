# Upstream gaps

These are things in the Voss repositories that limit what VossProofs can measure. Each one is a proposal for an upstream issue. VossProofs does not patch Voss. It works around each gap where it can and reports the limit where it can't.

Gaps 1 to 15 were checked against `origin/master` at `105a506b` (2026-10-17), and gaps 16 and 17 at `16f32ecb` (2026-10-18), unless a different branch is named.

| # | Gap | Effect on VossProofs | Current workaround |
|---|---|---|---|
| 1 | `voss eval` CLI, serve and SDK-client surfaces return an empty session record, so `cost_usd` and tokens come back null or zero. The Go and TS consumers print `cost_usd`, but the runner drops it. | Imported `voss eval` rows have unknown cost for those surfaces. | The `voss-serve` adapter reads `/session/{id}/cost` and the saved session record itself. |
| 2 | `voss eval` rows don't record output tokens. | Usage is incomplete in imported rows. | `output_tokens` stays null. Native runs read `completion_tokens` from the session record. |
| 3 | `voss do` builds a session record but never saves it. `--json` also forces auto-approve (`cli.py:2250`). | `voss do` can't serve as a measured Voss config. | Use `voss serve` for every Voss config. |
| 4 | The USD budget (`/budget`) is advisory. Only `token_budget` and `max_iterations` stop a run. `docs/protocol.md` advertises `POST /session/:id/budget` and `GET /session/:id/confidence`, and neither exists. | H5 (budget enforcement) can only be measured on tokens and turns. | Report the USD budget as not enforced. Measure overshoot against token budgets. |
| 5 | `voss team run` (board and EM) uses hardcoded deterministic reviewer and EM stubs, then blocks on an interactive `click.prompt` for approve/reject. The real Reviewer A and B are never instantiated outside `board/`. | Configuration C through the board can't run headlessly. | Phase 3 uses `POST /swarm` and `/swarm/{id}/run` for multi-agent configs. The board config is reported as "not evaluable". |
| 6 | Durable task replay (`/task-events`, `/capabilities`, `command_id`) exists only on the `go-tui-s4-session-memory` branch. | Can't rely on cursor replay or capability detection against master. | The adapter probes `/capabilities` (a 404 gives an empty list) and reads the legacy `/session/{id}/events` stream. |
| 7 | `budget.updated`, `confidence.updated` and `probable` events are defined in `contracts/events.schema.json` but never emitted. | No event-level budget or confidence telemetry. | Use per-run fields in the saved session record. |
| 8 | `voss.eval.runner.run_suite` resolves suites against the current directory and raises `click.UsageError`. Behavior depends on task-id prefixes: `05-` selects the resume path, and `py-`, `rust-` and `ts-` select the toolchain skip. | It can't be used as a library. | `voss eval` is called as a subprocess from a Voss checkout, and its `runs.jsonl` is imported. |
| 9 | Resolved on master: `evals/review-locked-2/` and rubric v2 replaced the first locked result. The first set's `freeze.json` still says rubric v1, while its dev report was rerun under v2. | Phase 2 must know which locked set and rubric are authoritative. | Phase 2 uses `evals/review-locked-2`. Each review record carries the rubric of the run that produced it. |
| 10 | voss-lang: `voss check` has no JSON output, and `voss-exec` runs workflows only through `cargo test`. Replay is its only binary command. | The runtime suite can use exit codes and replay parity only. | Phase 4 runtime suite: `voss-exec replay` over `tests/exec-fixtures`, plus `voss check` exit codes. |
| 11 | Voss-ADE: Tauri WebDriver isn't possible on macOS. Only `crates/core` can be tested headlessly. | No native UI evaluation. | An optional adapter for `cargo test -p voss-core`, labeled as not covering the UI. |
| 12 | Voss-OS runs only on Linux, through bubblewrap, Landlock and seccomp. | No OS-level sandbox for live runs on macOS. | Reported as a contamination threat (see methodology). A Linux VM adapter is optional in Phase 4+. |
| 13 | `voss/__init__.py` says `__version__ = "0.1.0"` while `pyproject.toml` says 0.1.2. | Run records carry an ambiguous Voss version. | Record what `voss --version` reports. A git SHA should be added once Voss exposes one. |
| 14 | `voss serve` decides between the agent loop and ambient chat with a keyword router (`voss/harness/ambient.py:85`). An imperative task that doesn't match its verb list goes to ambient chat. For example, "is_leap_year must follow the Gregorian rules ... Make it correct" has no file or shell access there, and the session still records `exit_reason: done`. Clients have no way to force a run. | Whether a task runs at all depends on prompt wording. That's a confound for any comparison against a baseline agent. | The adapter flags turns that never enter the `run` phase as `exit_reason: no-run`, with an error, and doesn't count them as claims. Prompts are not reworded to suit the router, because misrouting is a measured outcome. |
| 15 | The `claude-agent` provider reports `cost_usd: 0` and about 2 prompt tokens per iteration. The real context goes into `cache_creation_input_tokens`. | Subscription runs carry no usable cost signal, and prompt tokens alone understate usage by orders of magnitude. | A $0 cost on a run that used tokens is recorded as unknown. Cache creation and cache read tokens are stored separately. |
| 16 | `voss.eval.review baseline-b` records no cost, tokens or latency for Reviewer B. | Reviewer B's cost is unknown in every review report. | Recorded as unknown. |
| 17 | Each J4 split has 2 changes where every requirement is met, against 17 to 19 that should be rejected. | Change-level true accept has n=2. On false accepts alone, a reviewer that rejects everything looks perfect. | Reports show false accept and true accept together, include a reject-all baseline and mark n<10 rates as underpowered. Criterion-level supported recall (n=17) shows whether a reviewer accepts what it should. VossBench `oracle-jev` adds accept-worthy changes. |
| 18 | `/swarm/{id}/run` marks a native builder's task done when its turn ends, whether or not the builder did the work (`_run_native_builder` in `voss/harness/server/app.py`). In a live run, a builder assigned to "create a test script" only read files, and its task was still marked done before `swarm.complete`. | `swarm.complete` does not mean the plan was carried out. | `voss-swarm` treats `swarm.complete` as a completion claim only. Verification comes from the hidden checks. |
| 19 | The swarm coordinator splits the goal with an LLM call outside any session, and the swarm API takes no token or USD budget. | Configuration C's usage is undercounted by the task split, and only its wall-clock budget can match Baselines A and B. | Usage is summed over member sessions, and `cost_source` says it excludes the split. H5 comparisons that involve C use wall-clock time. |
| 20 | The swarm coordinator must split a goal into at least `min(2, builders)` tasks (`seed_tasks` in `voss/harness/swarm_coordinator.py`), and its prompt asks for "between 2 and 2" with the default two builders. On single-change tasks it invents a second task. In the gate run, that was an analysis file written outside the allowed paths. In the pagination smoke run, it was a test script that was never written. | Configuration C fails scope checks and inflates usage on tasks that should not be split, so it is measured against a handicap that has nothing to do with multi-agent work. | Reported as found. Scenario prompts are not reworded to avoid it. |
| 21 | On the default `legacy` memory backend, a `voss serve` turn gets no memory tools and no pinned memory (`voss/harness/server/app.py:404` attaches them only when the store is not a `MemoryStore`). Notes saved with `/save` land in `.voss/memory/notes`, and no later serve session reads them. | Across serve sessions, Voss carries only what is in the workspace files and `VOSS.md`, or the conversation when a client resumes a session. | The memory suite compares fresh and resumed sessions. Voss's own note store is reported as not read back. |
