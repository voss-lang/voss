## User config

Harness config lives under the user's config directory:

```text
~/.config/voss/config.toml
```

Use:

```bash
voss config
voss config --show
```

### `[instructions]`

Controls how `AGENTS.md` and `CLAUDE.md` are loaded into every native run (see `voss instructions show`).

```toml
[instructions]
enabled = true          # inject the bundle as the `## Instructions` prompt block
budget_tokens = 4000    # total budget; overflow is reported as instructions_overflow
per_file_tokens = 2000  # per-file cap applied before the total
read_global = false     # also read ~/.codex/AGENTS.md and ~/.claude/CLAUDE.md
```

Files load in this order: global (opt-in), project root `AGENTS.md` then `CLAUDE.md`, then each directory down to the target. A `CLAUDE.md` that only contains `@AGENTS.md` collapses into the file it imports. The bundle hash is recorded on every session and run.

### `[billing]`

Overrides the billing kind of an auth source. Automatic Observe investigations use call, token, and time limits for `subscription` sources and reserve dollars for `metered` ones.

```toml
[billing]
claude-agent = "subscription"   # default
codex-oauth = "subscription"    # default
env-anthropic = "metered"       # default
ollama = "unknown"
```

### `[judgments]`

Model and limits for opt-in Jev judgments. Defaults are 4 calls and $0.01 per turn.

```toml
[judgments]
max_calls_per_turn = 4
max_cost_usd = 0.01
timeout_ms = 5000
```

Judgments are switched on per project in `.voss/config.yml`, not here. See [Config and auth](/harness/config-auth#jev-judgments).

### MCP and skills

Voss imports MCP servers from Claude and Codex config. `~/.config/voss/mcp.yml` and project `.voss/mcp.yml` override imported entries. Skills come from user and project `.claude/skills`, `.codex/skills`, and `.agents/skills` folders; Voss's user `skills` folder and project `.voss/skills` take precedence.

## Project state

Durable project state is split between human-readable `VOSS.md` and machine-managed `.voss/` directories:

```text
VOSS.md
.voss/
  config.yml          # project opt-ins: judgments, retained memory backend
  constraints.yml
  mcp.yml             # MCP server overrides
  permissions.yml
  validation.yml
  principles.yml      # project engineering principles (orchestration)
  team.voss           # declared role roster (orchestration)
  skills/
  memory/
  plans/
  sessions/
  decisions/
  swarm/              # swarm state and candidate review results
  task-journal.sqlite3  # durable task events for voss serve clients
```

`VOSS.md` is injected into harness context at session start. Machine fences inside it let Voss update architecture notes without overwriting surrounding human prose.

`principles.yml` and `team.voss` drive the [orchestration layer](/orchestration/overview): `principles.yml` extends or overrides the six default [principles](/orchestration/principles), and `team.voss` declares the [role roster](/orchestration/team-config) validated by `voss team check`.

## Cache state

Rebuildable state belongs under `.voss-cache/`:

```text
.voss-cache/
  repo.idx
  harness/
  code/
```

You should be able to delete cache state and rebuild it. The `code/` directory holds the
derived code recall index used by `voss recall` and the `code_recall` tool; it is not the
curated project memory store.

## Session state

Current project sessions live under `.voss/sessions/`. Legacy sessions in the old user-state directory are read-only via `voss sessions --all`.

A team run also persists its [session tree](/orchestration/session-tree) here, one file per agent node, plus per-card review sidecars:

```text
.voss/sessions/
  <session_id>.json                 # harness session
  <session_id>/
    token-savings.jsonl             # estimated original vs packed context tokens
  <root_id>/
    <node_id>.json                  # session-tree node (budget, scope, status)
    <node_id>.review.json           # Reviewer-A + Reviewer-B sidecar
    judgments.json                  # advisory requirement assessments, when saved
```

Node and review files are written with `0o600` permissions.

`token-savings.jsonl` contains estimated counts only. It does not store prompt text, tool
arguments, or tool output.

<Note>
Do not commit secrets to `VOSS.md`, `.voss/`, or `.voss-cache/`. Voss avoids storing provider credentials, but prompt text and project notes are still local files.
</Note>
