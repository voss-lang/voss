The harness gives one agent a bounded loop. Orchestration extends the same boundaries to a whole team: declared roles, partitioned budget, scoped tools, independent review, and a replayable trail.

The promise:

> Voss lets AI agents work like an engineering team while keeping every action scoped, budgeted, reviewed, and replayable.

## The six primitives

Every run is built from the same six primitives.

| Primitive | Meaning | Where it lives |
| --- | --- | --- |
| Capabilities | The agent toolbelt — typed, permissioned, auditable | [`voss capabilities`](/reference/capabilities) |
| Principles | Engineering culture injected into every agent | [`.voss/principles.yml`](/orchestration/principles) |
| Orchestration | Delegation and integration | [Engineering Manager loop](/orchestration/em-loop) |
| Roles | Specialist lenses with their own scope and budget | [`.voss team{}`](/orchestration/team-config) |
| Memory | Institutional knowledge across runs | [Session tree](/orchestration/session-tree), project memory |
| Verification | The independent review loop | [Reviewer A/B](/orchestration/reviewers) |

## One run, end to end

```text
human idea
  -> EM derives cards
  -> assign roles from the declared roster
  -> partition budget down the session tree
  -> dispatch workers in parallel (within WIP limits)
  -> Reviewer-A authors the bar from the idea
  -> Reviewer-B judges narrative-blind
  -> board gates Done on independent review
  -> RunFinal record + review sidecars persisted
```

## The MVP flow

A team is declared once in `.voss`, then a single goal runs through the cage.

```bash
voss team check
voss team run "Add password reset flow with tests"
voss board
voss review
voss audit
```

<Note>
Today `voss team run` drives the board with a scripted EM and placeholder reviewers that always pass. It exercises the real team config, session tree, gates, audit, and human sign-off, but it does not do the work itself. The board's worker pipeline is planned for a later phase. Live multi-agent work runs as a [swarm](#swarms).
</Note>

This run proves the core invariants:

- The EM cannot invent roles outside the declared roster.
- Workers cannot write outside their assigned scope.
- Budget cannot be oversold — it is enforced down the session tree.
- Agents cannot mark their own work Done.
- Done requires independent reviewer evidence.

## Swarms

A swarm is the live multi-agent path. A client creates one through the `voss serve` swarm routes (`POST /swarm`, or `create_swarm` in the Rust SDK), and the default roster is a coordinator, two builders, and a reviewer. The coordinator splits the goal into tasks, each with owned files; two active tasks may not own the same file unless one depends on the other. Builders can be native Voss agents or headless Claude Code and Codex sessions, each working in its own worktree, and writes outside a task's owned files are denied.

When a task finishes, its work becomes a candidate for review. Candidate-ready means review is pending, not that the work is merged or accepted. Projects with `judgments.review: shadow` also get an advisory Jev [requirement assessment](/orchestration/reviewers#requirement-assessments) for each candidate.

Every swarm run is recorded as a task graph in the task journal: declared dependencies, scope, criteria, and each worker attempt with its role, model, worktree, and review state. Clients replay it by cursor, and an interrupted run is marked interrupted rather than relaunched.
